What does every part of a GenHTTP server have in common?

Every part of GenHTTP is the same two-method IHandler: PrepareAsync warms the tree once before the first connection, HandleAsync answers the request. The lever frame is the builder, the points are the segment match, and every road ends somewhere — a response, or the dead spur that becomes a 404.

How it works

IHandler · A4 · 2 / 2
01

Two methods, one tree

The train enters at the root. PrepareAsync warmed every road once before the first connection; now HandleAsync answers.

02

The points set

The segment match throws the points: .Add("files", handler) hung this platform on the branch when the tree was built.

03

Every road ends somewhere

api, files, spa — webservices, asset trees, single-page apps. All handlers, so all of them compose.

04

The dead spur

No handler claims the road, so HandleAsync returns null — and the concern chain around the tree turns that into a 404.

05

One address per page

At the root the layout forces a trailing slash by redirecting, so the same content is never served at two URLs.

Why one interface?

One two-method contract from the socket to your lambda means every module composes with every other by construction — no middleware interface distinct from handlers, no special case for the root, no hidden global state. That is also what makes the three-engine promise testable.
